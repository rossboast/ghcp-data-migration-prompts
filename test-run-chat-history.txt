GitHub Copilot: ## Design Rationale - Phase 5 Migration Framework

Here's the thinking behind what we've built:

### 🎯 Core Philosophy: "Build Once, Use Everywhere"

The framework follows a **layered architecture** where each layer has a clear responsibility and consistent patterns. This eliminates code duplication and makes the codebase predictable.

---

### 📐 Architectural Decisions

#### 1. **Template Method Pattern in Base Classes**
**Why?** Every ETL component needs logging, metrics, and error handling - but implementing this in every class creates duplication and inconsistency.

**Solution**: Base classes handle the "ceremony":
```python
# BaseExtractor.run_extraction() does this automatically:
1. Log start with context
2. Start metrics timer
3. Validate configuration
4. Call extract() ← Only this is implemented by concrete classes
5. Log completion with record counts
6. Stop metrics timer
7. Handle errors with context
```

**Benefit**: Concrete classes focus on business logic (JDBC queries, transformations) while base classes ensure observability.

---

#### 2. **Singleton SparkSession**
**Why?** PySpark crashes if multiple SparkContexts exist. Every component needs the same session.

**Solution**: `SparkSessionManager` singleton with lazy initialization:
- First call creates session with Oracle JDBC + Cosmos connector
- Subsequent calls return existing session
- Environment-driven configuration (dev/prod settings)

**Benefit**: Zero chance of "SparkContext already exists" errors, consistent configuration across all components.

---

#### 3. **Dataclass-Based Configuration**
**Why?** Connection strings, credentials, and settings vary by environment (dev/staging/prod). Hard-coding is dangerous.

**Solution**: Type-safe dataclasses with environment loading:
```python
@dataclass
class OracleConnectionConfig:
    host: str
    port: int
    service: str
    
    @property
    def jdbc_url(self) -> str:
        return f"jdbc:oracle:thin:@{self.host}:{self.port}/{self.service}"
```

**Benefit**: IDE autocomplete, type checking, easy testing with mock configs, secure credential management.

---

#### 4. **Centralized Schema Definitions**
**Why?** Oracle has 7 tables with ~50 columns. Defining schemas inline in every extractor/transformer creates maintenance nightmares.

**Solution**: Single source of truth in `schema_definitions.py`:
- `OracleSchemas.employees` - PySpark StructType for extraction
- `CosmosSchemas.employee_document` - Target document structure

**Benefit**: Change schema once, all components updated. Easy to validate source vs target compatibility.

---

#### 5. **Metrics Collection at Every Layer**
**Why?** Migration debugging requires knowing: "Which phase failed? How many records? How long did it take?"

**Solution**: `MetricsCollector` automatically tracks:
- Records extracted/transformed/validated/loaded
- Execution time per component
- Error counts and types
- Cosmos RU consumption

**Benefit**: Instant visibility into pipeline health, easy to identify bottlenecks, audit trail for production runs.

---

#### 6. **Structured Logging with Context**
**Why?** Text logs are painful to parse. Need to filter by component, operation, or feed.

**Solution**: Structlog with JSON output + context binding:
```json
{
  "timestamp": "2025-10-22T10:15:30Z",
  "level": "INFO",
  "component": "oracle_extractor",
  "operation": "extract_employees",
  "message": "Extracted 107 records",
  "execution_time": 2.3
}
```

**Benefit**: Easy log aggregation (Splunk/ELK), filterable queries, automatic context propagation.

---

#### 7. **Validation as First-Class Citizen**
**Why?** Bad data in Cosmos is expensive to fix. Need to catch issues before load.

**Solution**: Three validation levels:
- **Field validators**: Null checks, format validation (email regex)
- **Record validators**: Referential integrity (FK checks)
- **Business rule validators**: Salary ranges, circular manager detection

**Benefit**: Data quality guarantees, early error detection, detailed validation reports.

---

#### 8. **Batch Processing with Configurable Sizes**
**Why?** Loading 107 employees is fine in one batch. Loading 10M records requires batching to avoid memory issues.

**Solution**: `BaseLoader` auto-splits DataFrames:

```sql
employees

  LEFT JOIN departments ON emp.department_id = dept.department_id
  LEFT JOIN jobs ON emp.job_id = job.job_id
  LEFT JOIN locations ON dept.location_id = loc.location_id
  LEFT JOIN countries ON loc.country_id = country.country_id
  LEFT JOIN regions ON country.region_id = region.region_id
  LEFT JOIN (
    SELECT employee_id, collect_list(struct(...)) AS job_history
    FROM job_history
    GROUP BY employee_id
  ) AS history ON emp.employee_id = history.employee_id
```
